# Design Proposal: a secrets consumption contract, independent of the secrets manager

> Tracking issue: [OKDP/OKDP#43](https://github.com/OKDP/OKDP/issues/43)
> Status: **PROPOSED**

## 1. Problem

OKDP packages already read their secrets from Kubernetes Secrets. What is missing is a rule for
how those Secrets are shaped, where they live and where they come from. Each part of the platform
made its own assumptions:

- the sandbox copies every Secret to every namespace;
- the keys a package expects are only written in a description;
- some packages take secret values as plain Release parameters;
- the Control Plane only knows Vault.

So moving to another secrets manager, or keeping projects from reading each other's secrets,
means changing packages. Goal: packages depend on a contract, and the secrets manager can change
without touching them.

## 2. Current state

| Area | What exists | Reference |
|---|---|---|
| Sandbox secrets | `local-secrets-provider` creates Secrets from a list of values given as Release parameters. Each one carries `replicator.v1.mittwald.de/replicate-to: "*"`, so every `creds-*` Secret lands in every namespace, `kube-system` included. Empty values are filled by the mittwald secret-generator | `helm-charts-utilities/charts/local-secrets-provider`, `sandbox-dependencies/packages/system/tools` |
| Shared storage credentials | The optional SeaweedFS Secret is also replicated to `*`, so that project `s3` Connections can reference it | `okdp-sandbox/clusters/sandbox/optional/storage/storage.yaml` |
| Contracts | `secretRef` is a `type: string`. The expected keys (`username`/`password`, `accessKey`/`secretKey`) are only in a `description`. Nothing checks them before a pod fails | `okdp-sandbox/clusters/sandbox/contracts/contracts.yaml` |
| Values in parameters | The Keycloak package takes the admin password, user passwords and client secrets as parameters. In the sandbox, the same client secrets are declared again in `local-secrets-provider` | `sandbox-dependencies/packages/system/keycloak`, `okdp-sandbox/clusters/sandbox/releases/keycloak.yaml` |
| Control Plane | One `SecretStore` per project namespace, provider `vault` only, written in `external-secrets.io/v1beta1`. Console connections store their credentials in a `<name>-credentials` Secret of the project | `okdp-control-plane-server/internal/service/secret_store_service.go`, `docs/proposals/connections.md` |
| Console | The secret store form is Vault-specific | `okdp-control-plane-ui/src/features/project-console/secret-stores` |
| ESO | External Secrets Operator 0.15.1 is installed in the sandbox. ESO 2.12 serves the `v1` API, which is also its storage version, and no longer serves `v1beta1` by default. Chart 2.12.0 can still serve it through `crds.unsafeServeV1Beta1`, a deprecated flag meant for temporary use only | `sandbox-dependencies/packages/system/external-secrets` |

## 3. Decisions

| Question | Decision | Why |
|---|---|---|
| What a package consumes | A Kubernetes Secret in its own namespace, with keys fixed by the contract | Every chart already reads Secrets (environment variables, `existingSecret`). Mounting files from the backend (Secrets Store CSI Driver) would mean rewriting packages |
| Who provides the secrets manager | The platform, outside OKDP | Same line as object storage: OKDP consumes, it does not deploy or operate the backend |
| Where the contract is defined | Here, independent of any deployment engine | KuboCD can validate it. Another engine must be able to do the same |
| How Secrets reach a namespace | External Secrets Operator, as the reference implementation | Standard, many backends, already installed in the sandbox. The contract does not depend on it |
| Who picks the store | The platform configuration, never the package | Changing the backend must not touch packages |
| Isolation unit | The project namespace, enforced by Kubernetes RBAC **and** by the backend policy | A store per project proves nothing if two stores share one identity |
| Generated secrets | Generated once, never regenerated by a redeploy | A new value breaks what the old one protected: encrypted data, created users |
| Control Plane | Follows the contract, holds no backend-specific logic | Otherwise the server needs code for each secrets manager |

## 4. The contract

Sections 4.1 to 4.6 are normative. They apply to every package that consumes a secret, whatever
the deployment engine and the secrets manager.

Two roles are kept apart:

- a **consuming package** reads Kubernetes Secrets and nothing else. It depends neither on the
  secrets manager nor on the mechanism that produces the Secrets;
- a **producer** turns values from the secrets manager, or from a generator, into Kubernetes
  Secrets. ESO is the producer of the reference implementation (section 5).

A package that also produces some of its own secrets depends on the producer for that part
(section 5.3).

### 4.1 Reference

A package receives a secret as the **name** of a Kubernetes Secret in its own namespace. The
reference holds nothing else: no namespace, no key, no value.

### 4.2 Keys

The contract fixes the key names. The Secret must carry them. Extra keys are allowed and ignored.
A source that uses other names is remapped when the Secret is produced, never in the package.

| Shape | Required keys | Examples of use |
|---|---|---|
| Credentials | `username`, `password` | `database-server` contract, admin accounts. Same keys as the Kubernetes `kubernetes.io/basic-auth` type |
| S3 | `accessKey`, `secretKey` | `s3` contract |
| OIDC client | `client_id`, `client_secret` | OIDC clients of the services |
| Package-specific | documented by the package | a full connection string, a token |

A new shape is added to this table before a package uses it.

### 4.3 Location

The Secret lives in the namespace of the consumer. No Secret is copied to all namespaces. When a
Secret really has to be shared, it is delivered by name to each target namespace, and the
targets are listed explicitly.

### 4.4 No values in parameters

A consuming package never takes a secret value as a parameter. It only takes references. This
does not apply to a backend stand-in such as `local-secrets-provider`, which is by definition
where the values are stored.

### 4.5 Lifecycle

Each secret a package consumes has a documented lifecycle:

- **`immutable`**: the value never changes once created. A redeploy or a reconciliation must not
  replace it.
- **`rotatable`**: the value can change. The package documents how it picks up the new value
  (live reload, or restart needed).

The contract fixes the behaviour, not where it is written. Until a schema language can carry it,
the package documentation does.

The contract does not promise an automatic restart when a value changes.

### 4.6 Isolation

The identity used to fetch the secrets of a project cannot read the secrets of another project.
This holds at two levels: Kubernetes RBAC, and the policy of the backend. It is shown by a
negative test (section 8), not inferred from the resource layout.

## 5. Reference implementation: External Secrets Operator

This section is not part of the contract. It describes one way to satisfy it. Another
implementation is valid as long as section 4 holds.

### 5.1 Store selection

The platform configuration names the store each project uses. With KuboCD, this is a field of
the Context that applies to the project namespace, for example:

```yaml
secrets:
  store:
    kind: SecretStore
    name: project-secrets
```

A package that creates an `ExternalSecret` reads this field. It never names a store itself.

### 5.2 One store per project

- Each project namespace has its own `SecretStore`.
- The store authenticates with a ServiceAccount of that namespace.
- On a backend with Kubernetes authentication (Vault and compatible backends), the backend role is
  bound to that ServiceAccount and namespace, and its policy only allows the project's paths.
- Platform services use stores in their own namespaces. A `ClusterSecretStore`, if any, is
  restricted with `conditions` so that no project namespace can use it.

### 5.3 Who creates the `ExternalSecret`

| Secret | Created by | Example |
|---|---|---|
| Provided by an operator or a user | the platform (GitOps manifests, or the console through the server), next to the consumer | database credentials, external S3 keys |
| Owned by the package | the package, against the designated store or a generator | a generated encryption key, a configuration file rebuilt from several Secrets |

In both cases the consuming workload only sees the resulting Secret.

A package that creates `ExternalSecret` or generator resources depends on ESO for that part. It
keeps them in a separate template and declares the dependency on ESO. Its workloads still only
read the resulting Secrets, so replacing ESO means changing that template only. Whether such
secrets should rather be declared by the package and produced by the platform is open question 1.

### 5.4 Paths

On backends that support paths, values are stored under `okdp/<namespace>/<service>/<name>`.
Each segment is a DNS label (`[a-z0-9-]`). The project is the namespace, so platform services
follow the same rule.

The sandbox stand-in becomes a backend like the others: values are stored in a backing namespace
per project (`okdp-secrets-<project>`), read through the ESO `kubernetes` provider, with a Role
limited to that namespace. The Secret name there is `<service>.<name>`. Segments contain no dot,
so the mapping is unambiguous.

### 5.5 Generated secrets

ESO `Password` generator (`generators.external-secrets.io/v1alpha1`), with an `ExternalSecret`
using `refreshPolicy: CreatedOnce` and a target that is `immutable: true` and
`creationPolicy: Orphan`. The value survives a redeploy and a re-created `ExternalSecret`.

This does not cover the loss of the target Secret itself. If it is deleted, `CreatedOnce` and
`Orphan` do not bring the old value back, and the generator may produce a new one. For an
encryption key or an admin password, a new value is not a recovery: it can break the
application. Recovery restores the original value, or follows a procedure specific to the
application.

Limit: the value only exists in the cluster. It is lost with the cluster and is not covered by a
backup of the secrets manager. A platform that needs it can push the value to the backend with a
`PushSecret`. That is an extension, not part of the contract.

### 5.6 Rotation

Four events, which happen at different times:

| Event | Who | What |
|---|---|---|
| Rotation | the backend or an operator | a new value exists in the source |
| Refresh | ESO | checks the source every `refreshInterval` |
| Sync | ESO | writes the new value into the Secret |
| Pick-up | the consumer | starts using the new value, as documented by the package |

Default `refreshInterval`: one hour. It is a polling period, not a rotation delay. A reloader
(the sandbox `tools` package ships one) can restart workloads on change. Using it is a platform
choice, not a guarantee of the contract.

### 5.7 Compatibility

The reference implementation is tested with ESO 2.12. Supported versions are listed in a
compatibility matrix of the ESO package, and each release of that package pins an exact chart
version. It uses `external-secrets.io/v1` for `ExternalSecret`, `SecretStore` and
`ClusterSecretStore`, and `v1alpha1` for generators and `PushSecret`.

## 6. Migration

The order matters only where stated. Each step is its own issue or PR, linked from #43.

1. ESO and the server move together, on the pinned chart 2.12.0, validated in the sandbox:
   1. ESO 2.12 is installed with `v1beta1` still served (`crds.unsafeServeV1Beta1: true`), and
      `v1` is checked to be the storage version of the CRDs.
   2. The server switches to `v1`.
   3. Existing resources are re-applied in `v1`.
   4. `status.storedVersions` of each ESO CRD is checked. `v1beta1` is turned off only once it
      is no longer listed.

   The flag is deprecated and may disappear in a later chart, so this bridge stays short.
2. The `database-server` and `s3` contracts declare their keys explicitly. The form depends on
   what the schema language supports (open question 2).
3. `local-secrets-provider` stops replicating to `*` and delivers each Secret to the namespaces
   that consume it. Then it becomes a backend read through ESO (section 5.4). Once no Secret
   carries the mittwald annotations, the replicator and the secret-generator can leave `tools`.
4. The optional storage credentials are delivered to listed project namespaces instead of `*`.
5. Keycloak reads its admin password, user passwords and client secrets from Secrets.
6. The server takes the store from the platform configuration and accepts providers other than
   Vault. The console form follows.
7. Each package in `platform-packages` and `community-packages` is checked against section 4,
   one PR per package when a change is needed.
8. Validation in the sandbox (section 8).

## 7. Out of scope

- Deploying, operating or backing up a secrets manager.
- Dynamic secrets, PKI, rotation driven by the backend.
- Delivering secrets as files mounted from the backend.
- The console's secret management features beyond removing the Vault-only assumption.

## 8. Verification

Run in the sandbox, with two backends: the local stand-in, and the optional Vault release.

- No Secret is replicated to all namespaces: no `replicate-to: "*"` annotation is left, and each
  Secret read by a workload exists only in the namespaces that consume it. The backing namespaces
  of the local stand-in hold the source values, and only the identities of their project can read
  them.
- Negative test: project A's store identity cannot read project B's secrets. Checked on the
  Kubernetes side (`kubectl auth can-i get secrets -n okdp-secrets-b --as
  system:serviceaccount:a:<sa>` answers `no`) and on the backend side (an `ExternalSecret` in A
  pointing at a path of B fails to sync).
- Once the same values exist in Vault, a project moves from the local stand-in to Vault by
  changing the platform configuration only. No package and no Release parameter changes. Copying
  the values is a migration step, not part of the test.
- `immutable`: redeploying the Release and re-creating the `ExternalSecret` leave the value
  unchanged.
- `rotatable`: a value changed in the backend reaches the Secret within the refresh interval, and
  the consumer picks it up as its package documents.
- No secret value remains in the parameters of a consuming Release.

## 9. Open questions

For the contract:

1. **Secrets a package owns** (a generated key, a rebuilt configuration file). Either the package
   produces them through the implementation (section 5.3), or it declares the need and the
   platform produces them. The second keeps every package independent of the producer, at the
   cost of a new declaration format.

For the reference implementation:

2. **A machine-checkable form for keys and lifecycle.** KuboCD's schema language has no place for
   them today (a typed `secretRef` would need a change in KuboCD). Until then, the package
   documentation carries them.
3. **Credentials entered in the console.** Today the server writes them as a Secret of the project.
   Should they go to the project's backend instead?
4. **Who creates the per-project store** when a project is created: the platform's GitOps
   configuration, or the Control Plane.
5. **Local stand-in layout.** One backing namespace per project (section 5.4), or a single
   namespace with RBAC per Secret.
